# 运行与数据约定

本文从原 README 拆出长期运行约定；日志分离按 2026-10-22 本地源码核对。接口参数见 [api.md](./api.md)，事件处理范围见[当前解析说明](./parsing.md)，升级与一次性修复见[历史问题](./history.md)。

## 启动、归档与数据库升级

`1.0.2` 修复后续礼物事件的盲盒数量与盈亏：显式识别盲盒，独立使用盲盒成本计算盈亏，
沿用现有月度、场次、15 分钟统计桶字段与盈亏“角”单位；流水算法及表结构不变。
升级后重启单个采集进程即可生效，不回补历史记录。字段与成本缺失回退见 [parsing.md](./parsing.md)。

运行后 FastAPI 会通过 Uvicorn 在 `APP_HOST:APP_PORT` 对外提供接口。
主进程每 5 分钟以 INFO 级别记录一次数据库连接池状态；服务退出时该观察任务随主运行协程取消。

重启后先查询配置房间的直播状态（每批最多 100 个 UID），按原房间顺序启动所有在播房间；等待这些房间收到成功的弹幕服务器鉴权响应后，再启动未开播或轮播房间。成功响应中合法缺失的“无直播间” UID 归入后组，不会导致无限重试；状态查询失败会重试。在播房间初始化或鉴权失败时，不会提前放行未开播房间。两组内部仍保留原来的 3 秒启动间隔。排序快照不提前修改 `LAST_STATUS`，开播场次仍由状态监听器创建。每日重连只处理已启动的客户端，避免在启动阶段绕过顺序或重复创建连接。

房间 WebSocket 与 B 站 HTTP 请求共用会话和 Cookies。共享 `TCPConnector` 显式设置 `limit=0`，取消默认的 100 个总连接上限，避免长连接占满连接池后，直播状态、同接、守护、粉丝等请求尚未发送就排队超时；运行期间新增房间同样适用。房间配置、连接启动间隔、`getDanmuInfo` 限速与退避、业务轮询间隔及 HTTP 请求超时继续生效，无需新增环境变量。启动日志中的 `[session]` 会记录连接池上限；`[pool]` 日志仍仅表示数据库连接池状态。升级代码后需重启采集进程。

月末归档以场次开始月份为准：跨月仍在直播的场次及其 15 分钟数据保留在主表，确认下播后再整体迁移。月归档调度器每 5 分钟补扫历史场次，无需等到下个月或重启。自动归档保留 10 分钟结束缓冲，每轮先固定已经结束的候选场次，再等待结束快照队列排空、重试待写场次弹幕；等待期间才确认下播的场次留到下轮，避免旧结束时间绕过保护。队列等待超过 120 秒或场次弹幕仍未写入时，本轮暂缓并记录告警，下轮继续。因此正常情况下跨月场次在结束后约 10～15 分钟归档；队列积压或数据库故障时可能延后。父表、15 分钟子表使用相同的候选场次和结束截止时间，先归档子表，再归档父表；手工归档 CLI 不使用自动结束缓冲。

从 **1.0.5** 起，首次发现普通下播或收到 `CUT_OFF` / `ROOM_LOCK` 时，立即启动独立异步任务，并发采集结束守护数（舰长、提督、总督）、粉丝团人数和关注数，缓存于进程内；不等待周期采集队列，也不提前写入场次结束字段。180 秒宽限期结束确认关闭场次时，写入该次下播快照，不再重新请求这些指标。这里的即时采集指发现下播后发起 HTTP 请求，仍受状态轮询和接口响应耗时影响，不能恢复平台实际下播时刻的历史值。

宽限期内重开会取消尚未完成的采集并丢弃旧快照，保持原场次；再次下播时重新采集。重复下播事件不重复采集。各字段独立处理采集失败，保留成功字段和真实零值，失败字段留空并记录告警，不用宽限期结束时的新值或旧周期缓存冒充。若确认结束时采集尚未完成，返回后再写入已关闭场次，自动归档在原有 120 秒等待预算内等待该任务；超时暂缓归档，不取消采集。快照仅驻留内存，重启后无法恢复丢失快照，也不补采三分钟后的数据；正常退出会取消剩余任务。

`room_live_stats` 的礼物、上舰和 SC 金额列在 ORM 中分别声明为 `DECIMAL(20,1)`、`DECIMAL(20,0)`、`DECIMAL(20,0)`。启动时只补不存在的列，**不会修改现有表的列类型，也不会截断已有金额**。升级旧库须在数据库备份后手动迁移主表及已有 `room_live_stats_YYYYMM` 归档表：先用 `TRUNCATE(gift, 1)` 舍去礼物百分位及以后的小数，再修改列类型。MySQL 类型转换会重建表并阻塞该表写入，请在停止相关写入的维护窗口执行；只改 ORM 或重启服务不能修复旧列。

## 公开健康检查

`GET /health/check` 无需鉴权。后台线程每轮结束后等待 15 秒，使用独立短连接执行 MySQL `SELECT 1`、对配置的 Redis DB 及 DB1/DB2 执行 PING，并通过采集事件循环获取房间、HTTP 连接池与队列状态。数据库/Redis 连接、读写超时分别限定为 2 秒；采集循环快照等待最多 2 秒。探测只读且不占用业务数据库连接池，API 请求只读取最新采样结果，缓存或可见性 Redis 故障不会阻断健康检查。`[pool]` 的数据库指标与健康响应中的 `collector.http_pool` 分开观察。

所有当前检查通过返回 200；依赖、连接池、房间或启用的 API 缓存异常，或初始化未完成时返回 503；采样超过 45 秒未更新标为 `stale`。历史异常与当前状态分开，已恢复的历史错误不会单独改变当前总体状态；近一小时有观测的 B 站接口最近结果仍为失败时，总体状态会降级，后续成功后恢复，不额外主动探测 B 站。房间仅在当前 WebSocket 打开且鉴权成功时计为已连接，初始化中的房间也会使总体状态降级。

断联、主动关闭、B 站上游 HTTP/业务/解析/读取失败，以及本地业务 API 的 5xx/响应中断与 429，按秒聚合最近 3600 秒，最多附带 200 条最近事件。历史从当前进程启动开始累计，重启后清空；覆盖不足一小时时通过 `observed_since`、`coverage_seconds`、`full_window` 标明。完整结构、故障统计口径及外部网络故障边界见 [API 文档](./api.md#11-get-healthcheck)。升级代码并重启采集进程后开始采集，无需新增环境变量。

## Cookies 失效告警

礼物消息出现 `uid=0`，或守护人数接口 `GUARD_API` 返回 `code=-101`（账号未登录）时，使用现有 SMTP 配置异步发送 Cookies 失效告警邮件，邮件附带触发日志。两种信号共用去重标记，每个进程生命周期最多尝试发送一次；发送失败仅记录日志，沿用原有不重试策略。更新 Cookies 后需重启采集服务。

`GUARD_API` 返回非零或缺失业务错误码时，本次守护人数视为获取失败，不将错误响应记录为三个零值；其他错误码仅记录日志，不触发 Cookies 失效邮件。

## 弹幕连接的 -352 退避重试

所有房间的 `getDanmuInfo` 首次请求和重试共用请求入口，任意相邻两次 HTTP 请求的发起时间至少间隔 **3 秒**，同一时间仅允许一个请求。该限制在同一采集进程的事件循环内生效，跨 `ClientSession` 共享；不同进程或不同部署不会自动共享额度。其他统计接口、已建立的 WebSocket 与心跳不经过此入口。

返回 `code=-352` 后保留当前初始化任务，单房间按 **3、6、12、24、48 秒**退避，后续保持 48 秒；实际请求还必须等待共享限速和熔断冷却。每个会话的连续风控恢复过程只主动清空并刷新一次 WBI 缓存，后续失败不反复刷新；成功获取有效配置后重置刷新额度，旧签名代次的失败不会清空新签名。

弹幕配置请求单独熔断：30 秒内连续失败涉及 3 间不同房间、WBI 风控刷新后仍返回 `-352`，或 `-352` 响应带 `X-Bili-Gaia-Vvoucher` 时，暂停该入口 **60 秒**。冷却后只放行一个探测请求，失败重新冷却，成功后恢复 3 秒间隔；成功同时清空累计失败记录。不会关闭健康连接，也不会暂停守护、粉丝团、关注或直播状态查询。

诊断日志记录房间、接口、HTTP 状态、真实业务 `code` 和风控响应头是否存在，不输出响应体、Cookie、token、签名、完整 URL 或风控凭据值。恢复期间出现临时网络/响应错误或 WBI 获取失败时继续等待恢复；未进入风控恢复时的其他错误沿用原失败处理。停止或删除客户端可取消退避、限速及熔断等待。

## 日志分离与归档

`1.0.3` 在现有单进程中分流日志，不增加采集实例：

| 日志 | 写入与管理 |
| --- | --- |
| 宝塔 `/www/wwwlogs/python/VR_douchong/error.log` | 礼物、上舰、SC、B 站连接、直播状态、归档和通用运行日志继续输出到控制台，由宝塔原有 stdout/stderr 重定向及项目日志切割接管；应用不直接打开此文件 |
| 项目根目录 `logs/api.log` | 应用直接写入 API 请求、API/缓存异常及 Uvicorn 运行日志，不向控制台重复传播，由应用独立进行大小轮转 |

`API_LOG_PATH` 留空时固定使用项目根目录的 `logs/api.log`，不随启动目录或 `ENV_FILE` 改变；显式相对路径则以实际 `.env` 所在目录为基准，也支持绝对路径。`API_LOG_PROJECT_NAME` 默认 `VR_douchong`，只用于归档文件名前缀。启动时创建日志文件及 `api-history_logs/`，项目运行用户需要有创建、追加和重命名权限；不可写时启动失败，不静默退回混合日志。仅导入模块不会创建文件。`logs/` 已排除出 Git。

单文件阈值为 **50 MiB（52,428,800 字节）**。下一条记录会使非空文件达到阈值时，先关闭并重命名旧文件，再向新的 `api.log` 追加。按 UTF-8 实际字节计算，单条记录保持完整（单条异常超大记录允许超过阈值）。重启后继续检查已有文件大小；归档不自动删除或压缩。默认示例：

```text
logs/api.log
logs/api-history_logs/VR_douchong_2026-10-09_194002_log.log
```

归档时间使用上海时区；同秒文件已存在则追加 `_001`、`_002` 等序号，不覆盖旧文件。API 归档目录与宝塔业务日志归档分开；通过文件管理或终端查看 API 日志，不假定宝塔项目日志页自动识别自定义文件。不要再给 `api.log` 配置宝塔切割或外部轮转，避免两个机制操作同一文件；`error.log` 继续由宝塔按原设置处理。

每个进入 ASGI 应用的 HTTP 请求记录一次 JSON 访问消息，包括上海时区毫秒级 `request_time`、随机 `request_id`（日志前缀）、可信代理规则下的客户端 IP、方法、路径、业务查询参数、状态码、`duration_ms` 和响应完成状态。查询参数只记录 `month`、`room_id`、`uid`、`cache`（值最多 128 字符，查询字段超过 64 个时省略参数）；不记录认证头、请求体或原始查询串，换行等控制字符由 JSON 转义。Uvicorn 默认访问行关闭，保留其运行/异常日志。

计时从应用收到请求到最后一段响应体交给服务器，包括缓存、限流和流式响应，不包括后续后台任务或客户端完成下载的时间。日志层包在 FastAPI 外侧，覆盖缓存直接返回、400/429/503、404/405 和异常 500；未完成的响应记录 `completed=false` 和异常类型（如有），尚未发送状态码时为 `null`。未进入应用的协议错误由 Uvicorn 记录；Nginx 自行返回的 502 等需检查 Nginx 日志。

API 上下文随请求进入同步工作线程和主循环管理操作；缓存构建线程也标记为 API 工作。API 新增房间启动长期 WS 任务前清除该上下文，确保之后的礼物和采集写库日志继续归入 `error.log`。周期连接池观察等后台采集日志仍归原日志。缓存故障日志继续沿用现有限频，不增加正常刷新日志。

## 违规直播片段的有效时长

所有场次保留原有 180 秒下播宽限期，宽限期内重开沿用同一个 `session_id`。有效时长按每次实际开播的片段独立计算：开播期间收到 `WARNING`、`CUT_OFF` 或 `ROOM_LOCK` 时，该片段从开播到下播都不计入 `room_live_stats.duration`；同一个合并场次中其他正常片段的时长保留。有效天仍按同一自然日内正常片段累计满 7200 秒计算。礼物、上舰、SC、弹幕、合并场次起止时间和其他场次统计继续按原规则记录。

- `WARNING` 使用事件中的 `roomid` 字段，只作废当前开播片段，不主动下播。状态轮询确认下播后进入宽限期，重新开播的片段恢复正常计时。例如 21:00 下播、21:01 重开，保持原场次 ID；21:00 前的违规片段无效，21:00～21:01 的下播间隔不计时，21:01 后的新片段有效。
- `CUT_OFF`、`ROOM_LOCK` 使用 `room_id` 和毫秒级 `send_time`，在事件时间停止当前片段并进入宽限期。`ROOM_LOCK` 仍遵守平台给出的锁定到期时间；若解除锁定时宽限期尚未结束，可沿用场次；否则在宽限期结束后关闭原场次，之后重开创建新场次。强制下播后，状态接口返回的旧开播时间不会恢复有效计时。
- 正好 180 秒仍可合并，超过 180 秒关闭原场次。重复违规事件只撤回一次当前片段的贡献；跨日、跨月已累计的该片段贡献也一并撤回。较早正常片段的时长不会因后续片段违规被撤回，晚到的旧片段事件也不会作废新片段。

启动时自动为 `live_session` 及已有月归档表补充 `duration_valid`（默认 1）和 `duration_ledger`（可空 TEXT）两列。`duration_valid` 表示当前/最后一个开播片段是否有效；收到违规事件设为 0，宽限期内重新开播设回 1，不能用这个字段直接过滤整个合并场次来汇总有效时长。`duration_ledger` 的 JSON 中，`days` 保存整个合并场次已累计的有效秒数，`segment_days` 保存当前片段可撤回的贡献，`segment_start`/`segment_end` 保存当前片段边界，`end` 防止重复计时。恢复未结束场次时读取这些状态。部署需重启采集程序，并确保数据库账户具备补列权限。

此处理接收实时 WebSocket 事件，**不会自动回放 `downloads/error.log` 或修正部署前的历史违规场次**。部署前已写入的片段没有场次贡献台账，无法自动精确撤回；如需修正这些旧数据，应另行核对日志和数据库快照。

## API Redis 缓存与限流

正式运行默认开启 `API_CACHE_ENABLED=1`。六类 GET 查询只读取 Redis DB2 的缓存；原有两个房间管理 POST 保持原有鉴权与写入语义，另有两个临时隐藏/恢复 POST 只修改 Redis 可见状态。DB2 从 `REDIS_URL` 自动派生，即使 URL 路径或 `?db=` 指向其他库，也不会与 DB0 付费去重、DB1 鲸鱼指标混用。DB2 仍共享 Redis 进程的内存与持久化，并不是独立内存配额。

- 启动后后台预热全部已知月份及已知/配置房间的查询结果，不阻塞直播采集启动。完整预热完成前 GET 返回 `503`；未知但合法的月份/房间使用缓存空模板，不制造无限缓存键。
- 当前月默认每 10 秒刷新，按读取事务开始前的时间判断快照年龄；超过 30 秒、缓存缺失、数据损坏或 Redis 不可用均返回 `503` 和 `Retry-After: 1`，绝不直接回源 MySQL。时间约定与已有 MySQL `DATETIME` 一致，服务器应使用 `Asia/Shanghai` 本地时间。
- 基础数据、日统计、场次和区间批量读取。SC 按房间计数、最大 ID 及内容校验摘要判断变化，只重读变化房间；每 60 秒重新发现表并校准 SC 数据。未变化的 SC、场次、关注响应复用压缩结果。读取闭播区间是为了及时接收晚到的弹幕重试数据。
- 历史数据启动时全量预热；随后按 `API_CACHE_HISTORY_SECONDS`（默认 300 秒）检查 Redis DB2 的变更月份，只重读这些月份的六类数据并重建缓存，不再周期重读未变化月份。新发现的月份仍会首次预热；切月时将刚结束的月份加入完整历史刷新，即使它只更新过汇总或未留下变更标记。当前月刷新保持优先。历史汇总的最新房间信息直接复用当前基础快照，不重复扫描历史 SC。
- 历史月的 `live_session` 和 `live_session_15m_stats` 在同一只读一致性事务内合并主表与月归档表，保留跨月未下播场次及迟到分桶。先读主表，再即时检查归档表是否存在，兼容归档表刚创建或发现结果过期的情况；父表按 `id`、分桶按 `(session_id, bucket_index)` 去重，重复时以主表字段为准。两侧分别查询以兼容旧归档缺少可选列，缺失值继续按原接口返回 `null`。MySQL 5.7 在读取期间新建归档表可能返回 1412，此时关闭失败事务并重新读取整个历史月份，最多尝试 3 次；失败不发布部分快照，也不清除该月变更标记。合并只发生在该历史月份预热/变更刷新时，当前月仍仅查主表，不增加 10 秒刷新 SQL。迟到弹幕在分桶已归档且主表无同键记录时直接累加原归档桶，不新建覆盖其金额的主表记录。分桶归档先在锁定事务中检查同键记录：兼容列全部一致才允许去重；任一列不同则保留两侧、记录键值并暂缓该月这批子表归档，父场次也保留在主表等待处理。既不凭零金额猜测残缺，也不自动相加或用主表覆盖归档。
- 历史写入、迟到重试、场次快照/时长修正及归档在 MySQL 提交成功后按实际月份通知 DB2。命名空间内的 `dirty-months` 保存待处理月份，`history-revisions` 保存每次变更的随机版本，`history-changed-at` 保存 Redis 时间；不新增 MySQL 表或触发器。待处理标记不设 5 分钟过期，积压或失败后继续重试，成功发布后仅清除读取前捕获的同一版本，期间的新写入留到下一轮。正常归档不再广播全部历史月份。
- Redis 通知失败时，在当前进程保留月份并重试；进程重启后通过全量预热恢复。应保留 Redis 的持久化和 `noeviction` 策略。变更记录覆盖本应用写入；绕过本应用的手工 SQL、其他脚本或外部程序修改历史明细后，需要重启应用以全量预热，或在同一应用进程调用 `invalidate_history("YYYYMM")`，不能再依靠周期全量扫描自动发现。直接手工修改月汇总的变化仍可被当前基础快照比较发现。
- `GET /gift/by_month?year=YYYY` 的年度结果也缓存于 DB2，使用 `<前缀>:year:YYYY` 指向压缩汇总分代，与月份分代共享内存预算。启动时结合全量预热的月数据生成；当前年度随约 10 秒的当前快照更新，历史月份变更刷新成功后更新所属年份，其他历史年份仅在汇总/基础资料变化或缓存丢失时重新发布。复用现有月收入、月弹幕及保留在内存的日统计小计，不增加 MySQL 查询，也不随年度更新重读历史明细。新发现月份的小计尚未读取时，暂缓其年份的新版本发布；年度发布失败时保留对应月份变更标记。历史轮询会同时核对历史年度的 Redis 正文、空模板和校验值；发现损坏时用内存中保留的结果重新发布，不查询 MySQL。
- API/缓存 SQL 共用 Redis 滚动预算，任意滚动秒最多 9 条；连接设置、元数据、事务控制和重试 SQL 也计入。直播采集、归档、启动 schema 检查不在这个预算中。缓存构建使用额外一个专用读连接，原 `QueuePool` 的 `5 + 10`、30 秒等待、1800 秒回收保持不变。
- 同一 IP 对十个 API 合计每滚动秒最多放行 20 次，跨进程共享，超额返回 `429` 和 `Retry-After: 1`。这不是服务全局 20 次；另有每进程 32 个在途请求容量保护，过载返回 `503`，避免慢客户端持有过多大响应。
- 沿用 EO → 本机 Nginx → `127.0.0.1:4666`。Uvicorn 只信任回环代理；直接读取代理头时优先 `EO-Connecting-IP`，其次 `X-Real-IP`，不盲取 XFF 首项。源站必须限制 EO 回源，4666 端口不应对公网开放。Python 只能限流回源请求，EO 缓存命中不计入 Python 额度。
- 缓存按月分代原子发布，旧代短暂保留后回收，压缩 JSON 支持 gzip 和普通响应。`API_CACHE_MAX_BYTES` 默认 96 MiB，是应用缓存键预算；建议保留已有 Redis 持久化和 `noeviction` 策略，不允许全局淘汰 DB0/DB1 数据。不要长期关闭 API 缓存：`API_CACHE_ENABLED=0` 仅用于离线诊断，旧 GET 会直接访问数据库且不受缓存预算保护。
- 不记录正常预热/刷新/跳过日志；仅记录异常，按故障类别每分钟最多一次，日志不输出 SQL 参数、响应内容或凭据。内部指标保存在 `app.state.api_cache.metrics`。原业务、访问和连接池日志保持独立。

配置项及默认值见 `.env.example`。数据库 SQL、IP 请求和当前缓存年龄上限分别硬限制为不超过 9、20、30；填更大值不会放宽。当前正常响应及 429/503 使用 `Cache-Control: no-store`，避免 CDN 缓存错误响应或突破当前快照的新鲜度边界。

## 旧版重复分桶的升级检查

旧版可能在子桶归档后重新插入只有迟到弹幕的主表记录。它和合法的完整修正都可能与归档同键，金额为零不能用于区分来源。升级前可在选定业务库的只读副本执行 [audit_session_bucket_overlaps.sql](../scripts/audit_session_bucket_overlaps.sql)：该文件只查询元数据，返回每张月归档对应的 `audit_sql`；再逐条执行返回的 SELECT，按 `(session_id, bucket_index)` 对照两侧金额、付费人数和弹幕总数。查询不依赖父场次仍在主表，因此也能发现父场次已归档的孤立主表桶。

所有生成查询都没有重叠行，才表示该副本快照没有这类重复；副本需先追平。发现重叠时先核对事件来源、时间和完整记录，不自动选择主表、不直接相加。内容不一致的记录由归档保护保留，核实并修正后再重试归档；本补丁不执行生产数据修复。查询接口仍沿用主表优先的读取约定，因此未解决的存量冲突也可能继续影响场次分桶展示。年度/月度收入对账不读取分桶明细，不能替代本项检查。

## 房间临时隐藏与恢复

`app/room_visibility.py` 使用 Redis DB2 的 `<API_CACHE_PREFIX>:hidden-rooms` 集合保存房间号；隐藏通过 `SADD`、恢复通过 `SREM` 原子执行，不设 TTL。状态属于管理数据，不写进分代快照，不被预热和月份刷新删除；应用重启后继续读取，Redis 自身重启后的保留依赖部署的持久化配置。VR/PSP/VUP 共用 Redis 时必须使用不同的 `API_CACHE_PREFIX`；切换前缀或迁移 Redis 时应一起迁移隐藏集合。

最外层可见性中间件在每个 GET 请求读取一次当前集合，统一覆盖 Redis 缓存直接响应、gzip、访客查询和关闭缓存后的旧 MySQL 报表。汇总直接删除房间对象；单房间查询返回 404；按 UID 或时间窗口查询移除该房间的所有访客记录。无法读取可信状态时返回 503，不允许数据绕过隐藏规则。已开始的请求按自身读取到的状态处理。

完整缓存仍保留并刷新隐藏房间的数据，恢复只解除输出过滤，无需重扫历史表。采集房间配置、运行状态、MySQL 数据和归档均不修改；隐藏操作不调用原有删除房间生命周期，不停止或重新创建 blivedm 连接。接口只要求 JSON payload 的 `room_id` 和请求头鉴权，具体路径和幂等返回见 [API 文档](./api.md)。

## 访客进房记录

`config/rooms.json` 只管理 VR 的 WS 连接房间，`config/psp_rooms.json` 为 PSP 房间配置，`config/vup_rooms.json` 为 VUP 房间配置，通过 `ROOMS_JSON_PATH` 选择。`config/entry_users.json` 为独立访客名单，初始从 StarBot 导入 UID 和名称，此后直接维护本项目部署文件，不再同步 StarBot。

业务 JSON 默认放到实际 `.env` 所在目录下的 `config/`。房间和访客名单默认分别为 `config/rooms.json` 与 `config/entry_users.json`；可通过 `ROOMS_JSON_PATH`、`ENTRY_USERS_JSON_PATH` 指定其他路径，显式绝对路径保持原意，相对路径均以 `ENV_FILE` / `.env` 所在目录为基准，不受启动目录影响。升级时移动部署中的 JSON 并更新环境变量，不覆盖线上已有名单或房间。访客名单格式如下：

```json
[
  {"uid": 1203217682, "name": "泽音Melody"}
]
```

启动时读取，随后每小时完整校验并替换名单。非法或重复 UID、空名称、文件缺失或编辑期间 JSON 损坏时，保留上一次有效名单并告警；首次读取失败则暂不采集此功能。合法空数组表示暂停采集。增删名单无需重连，删除只停止之后的记录，不移除历史数据。

处理 `INTERACT_WORD` 和 `INTERACT_WORD_V2` 中 `msg_type=1` 的事件，只记录名单 UID。通过已有房间 UID 映射排除主播进入自己直播间；房主身份尚未知时暂不记录。未开播房间也可记录，范围限于程序实际建立的 WS 连接；无法补回断线、匿名 UID 或部署前的事件。

MySQL 新增 `room_entry_log`，仅保存 `room_id`、`uid`、`event_time`。三字段联合主键去重，月份根据事件时间确定，按月迁移至 `room_entry_log_YYYYMM`。时间沿用上海本地 DATETIME 约定，运行环境时区应为 `Asia/Shanghai`。有效上游秒/毫秒时间戳统一到毫秒精度；缺失或异常时间使用接收时间。相同房间、UID、时间戳的消息合并，不同时间的再次进入仍记录；缺失上游时间时不能精确跨协议去重。

事件回调仅入有界内存队列，后台批量写库；失败保留批次重试，正常退出尝试排空。进程突然退出可能丢失未提交事件，队列满会告警并丢弃新事件。数据库启动时自动创建新表，部署需包含新模型并重启程序；不改动既有业务表结构。

接口为 `GET /gift/entry`，支持房间/UID 月份查询，以及 `cache=1` 最近 10 分钟、`cache=2` 最近 1 小时查询。所有模式的访客 `items` 均从 Redis DB2 返回，不直接回源 MySQL；月度数据在分代缓存中存一份再按条件筛选，滚动窗口使用同一份最近 1 小时数据，月初从主表和上月归档补齐。历史读取合并主表残留与归档，迟到写入和归档触发历史缓存刷新；现有 SQL、内存及限流预算仍适用。完整参数和精简响应见 [API 文档](./api.md)。


仅 `/gift/entry?cache=1` 额外返回顶层 `red_pocket` 数组，空时为 `[]`。红包来自 `POPULARITY_RED_POCKET_V2_NEW`，暂存当前进程内存，不进入访客写库队列，不写 MySQL 或 Redis 历史快照，不参与礼物/上舰统计；重启后清空，不回放旧日志补齐。记录按房间和 `lot_id` 去重，以秒级 `start_time` 为 `event_time`，在 `start_time + 600 秒` 时固定过期，迟到推送不延长有效期。电池/礼物直接返回原始价格；舰长红包按约定四档价格映射数量，详见 [当前解析](./parsing.md)。其他 entry 查询和所有其他接口均不增加该字段；隐藏房间的红包同样过滤，访客查询的 Redis 缓存就绪与故障策略继续生效。
